# Bamboo Board Backend

대나무숲 콘셉트의 익명 게시판 서비스 백엔드입니다. 회원 인증부터 게시글·댓글·좋아요·신고, 조회수 동시성 제어와 무중단 배포까지 구현했습니다.

## 소개

Bamboo Board는 사용자가 부담 없이 글을 작성하고 서로의 의견을 나눌 수 있는 익명 커뮤니티입니다.

백엔드에서는 트래픽이 집중되는 게시글 조회를 Redis에서 먼저 처리하고, 변경된 조회수를 MySQL에 주기적으로 반영합니다. 이 과정에서 원자적 증가, dirty set, 분산 락, AOF를 적용해 여러 서버가 동시에 실행되는 환경에서도 조회수 유실을 방지했습니다.

좋아요는 사용자·게시글 조합에 유니크 제약 조건을 적용합니다.

## 데이터베이스 구조

최종 운영 구조는 `B3__current_schema.sql`에 V6 변경을 적용한 상태입니다. `post_counters`에는 좋아요·신고·댓글 수만 저장하고, 조회수는 `post_view_counts`로 분리했습니다. 기존 `post_counters.view_count` 컬럼은 `V4__remove_legacy_post_counter_view_count.sql`에서 제거하고, 좋아요 ID는 MySQL `AUTO_INCREMENT`를 사용하도록 `V6__use_identity_for_post_likes.sql`에서 통일했습니다. 이에 따라 Hibernate 보조 테이블인 `post_likes_seq`는 제거했습니다.

### 요구사항 분석
유저
- 이메일, 비밀번호, 닉네임, 프로필 이미지와 신고 누적 수를 관리합니다.
- 탈퇴 여부와 비밀번호 변경에 따른 인증 버전을 저장합니다.
- 한 유저는 여러 인증 세션을 가질 수 있습니다.

게시물
- 제목, 내용, 작성일시, 수정 여부, 고정 여부, 삭제 여부를 관리합니다.
- 작성자를 참조하고, 게시글 이미지·댓글·좋아요·신고와 관계를 맺습니다.
- 게시글 수정 충돌을 감지하기 위해 버전 값을 사용합니다.

댓글
- 내용과 작성일시를 저장하고, 작성자와 게시글을 참조합니다.

좋아요
- 좋아요를 누른 유저와 게시글을 참조합니다.
- 같은 유저가 같은 게시글에 중복으로 좋아요를 만들 수 없도록 유니크 제약 조건을 둡니다.

신고
- 신고한 유저와 신고 대상 게시글을 참조하고 생성 시각을 저장합니다.
- 같은 유저가 같은 게시글을 중복 신고할 수 없도록 유니크 제약 조건을 둡니다.

카운터
- 게시글 ID를 기본키이자 외래키로 사용하는 1:1 보조 테이블입니다.
- 좋아요 수, 신고 수, 댓글 수만 저장하며 조회수는 저장하지 않습니다.
- 좋아요·신고·댓글 변경 시 게시글과 별도 행을 갱신해 게시글 본문과 카운터의 경합을 줄입니다.

조회수
- `post_view_counts`가 MySQL의 조회수 기준값을 관리합니다.
- 게시글 조회 시 Redis에서 원자적으로 증가하고, 변경된 게시글을 dirty set으로 추적합니다.
- 스케줄러가 분산 락을 획득한 인스턴스에서 Redis 값을 MySQL에 반영하며, Redis AOF로 재시작 상황의 복구를 보완합니다.
- 목록 조회는 MySQL에 반영된 기준값을 사용하고, 상세 조회는 Redis의 최신값을 우선 사용합니다.

세션
- 로그인 시 리프레시 토큰 해시와 만료 시각을 `auth_sessions`에 저장합니다.
- 리프레시 토큰을 갱신할 때 토큰 해시를 교체하고, 로그아웃·폐기 시각을 기록합니다.
- 사용자와 세션은 1:N 관계이며 만료 시각과 폐기 여부로 활성 세션을 검증합니다.

게시글 이미지
- 게시글에 여러 이미지를 연결할 수 있습니다.
- 이미지 URL과 표시 순서를 저장하고, 게시글 삭제·수정 시 게시글과 함께 관리합니다.

## 트러블 슈팅

### 조회수와 댓글 수가 같은 행에서 경합하던 문제

초기에는 조회수·좋아요 수·댓글 수·신고 수를 `post_counters` 한 행에서 관리했습니다. 인기 게시글 하나에 조회 요청을 집중한 부하 테스트에서 조회수 자체는 원자적 `UPDATE view_count = view_count + 1`로 유실되지 않았지만, 같은 행을 갱신하는 댓글 요청까지 기다리게 되는 문제가 확인되었습니다.

개선 이전 조회·댓글 혼합 테스트에서는 `post_counters` 기본키 레코드에서 평균 1,721회의 행 락 대기가 발생했고, 댓글 생명주기 p95가 52ms, p99가 181.21ms까지 증가했습니다. 조회수 증가를 Redis의 원자적 `INCR`로 옮기고 MySQL의 조회수 저장 행을 `post_view_counts`로 분리한 뒤 같은 조건을 반복했습니다. 개선 이후 혼합 테스트에서는 행 락 대기가 0회로 측정되었고, 댓글 카운터와 조회수 증가량도 일치했습니다.

### Redis 증가와 MySQL 반영 사이의 정합성 문제

조회수는 요청마다 Redis에서 먼저 증가하고 MySQL에는 일정 주기로 반영하기 때문에 두 저장소의 값이 잠시 다를 수 있습니다. 또한 현재 조회수를 확인하고 증가시키고 dirty set에 게시글을 추가하는 작업을 자바 코드에서 여러 명령으로 나누면, 그 사이에 다른 요청이 끼어들 수 있었습니다.

조회수 증가, DB 기준값과 Redis 값의 비교, dirty set 기록을 Lua 스크립트로 묶어 Redis 내부에서 한 번에 실행했습니다. dirty set의 게시글을 대상으로 Redis 스냅샷 값을 확보하고 MySQL 커밋을 하나의 트랜잭션으로 처리했으며, 반영 후 Redis의 현재값과 스냅샷이 같은 경우에만 dirty set에서 제거했습니다. 값이 달라졌다면 이후 반영 대상에 남겼습니다.

배포용 Redis에는 AOF를 설정하고, 재시작 후 조회수와 dirty set이 복구되는 통합 테스트도 추가했습니다. 조회수 증가 중 Redis 연결 오류가 발생하면 마지막으로 확인한 DB 기준값을 반환하고, 주기적인 MySQL 반영에 실패하면 dirty 표시를 남겨 다음 주기에 다시 시도합니다. 입력값 검증 오류는 Redis 장애에 대한 대체 경로로 처리하지 않습니다.

### 여러 백엔드가 동시에 조회수 반영 작업을 실행할 수 있던 문제

스케줄러는 모든 백엔드 인스턴스에서 실행되므로 서버가 여러 대가 되면 같은 dirty set을 여러 서버가 동시에 MySQL에 반영할 수 있습니다. 서버 한 대에서만 실행되도록 JVM 내부 락만 사용하면 다른 서버의 작업을 막을 수 없습니다.

Redis에 분산 락을 두고 반영 작업을 시작하기 전에 `tryLock()`으로 락을 획득하도록 했습니다. 락을 얻은 인스턴스만 반영 작업을 수행하고, 다른 인스턴스는 해당 주기의 작업을 건너뜁니다. 반영 대상은 멱등적으로 저장하고 정상적으로 작업이 끝나면 `finally`에서 락을 해제합니다. 현재 애플리케이션 코드에서는 별도의 lease 시간을 직접 지정하지 않으므로, 장애 시 락 해제 정책은 사용하는 Redisson 설정에 의존합니다.

### 엔티티와 운영 데이터베이스 구조가 어긋나던 문제

기존 스키마를 기준으로 하는 `B3__current_schema.sql`을 정리하고, `V4__remove_legacy_post_counter_view_count.sql` 마이그레이션을 추가했습니다. 테스트 초기 데이터와 엔티티도 같은 구조로 맞추고 `ddl-auto`를 `validate`로 설정해 애플리케이션이 예상하지 못한 스키마로 조용히 실행되지 않도록 했습니다.

### H2에서 통과한 테스트가 MySQL 동작을 보장하지 못하던 문제

H2와 MySQL은 SQL 문법과 잠금 동작이 다를 수 있어 H2 테스트만 통과해도 운영 MySQL에서 같은 결과를 보장할 수 없었습니다. 특히 원자적 업데이트, 행 잠금, Flyway 스키마 검증은 실제 MySQL 환경에서 확인할 필요가 있었습니다.

일반 테스트는 인메모리 H2 데이터베이스를 사용해 빠르게 실행하고, MySQL 통합 테스트는 Testcontainers가 생성한 실제 MySQL 환경에서 스키마와 데이터 정합성을 검증합니다. Redis 통합 테스트는 별도의 Redis 컨테이너에서 조회수 증가와 재시작 후 데이터 복구를 확인합니다. 단위 테스트는 도메인 규칙과 예외 흐름을 확인하고, 통합 테스트는 데이터베이스·Redis 연동과 실제 데이터 정합성을 확인하는 식으로 테스트의 역할을 나누었습니다.

### 프론트엔드와 백엔드의 오류 응답 형식이 달랐던 문제

컨트롤러에서 발생한 오류와 인증 필터에서 발생한 오류가 서로 다른 JSON 형태로 반환되어 프론트엔드가 여러 필드를 순서대로 확인해야 했습니다. 또한 내부 오류 코드가 그대로 사용자에게 노출되는 경우도 있었습니다.

예외 응답을 `code`, `message`, `status`로 통일하고, 전역 예외 처리기·인증 필터·보안 설정에서 같은 응답 작성 방식을 사용하도록 수정했습니다. 프론트엔드는 `code`를 기준으로 표시 문구를 선택하게 하여 백엔드의 내부 문구와 사용자 문구를 분리했습니다.

## 프로젝트 후기

처음에는 API가 정상적으로 동작하는지 확인하는 데 집중했습니다. 하지만 기능이 늘어나면서 예외 처리, 데이터베이스 구조, 배포 환경까지 함께 고려해야 실제 서비스에 가까워진다는 것을 느꼈습니다. 구현한 코드가 실행되는 것과 운영 환경에서 안전하게 동작하는 것은 다른 문제였습니다.

가장 큰 전환점은 조회수 동시성 문제를 직접 부하 테스트로 확인한 경험이었습니다. 기존 원자적 UPDATE는 조회수 유실을 막았지만, 인기 게시글의 조회 요청이 댓글 처리까지 지연시키고 있었습니다. 이 결과를 바탕으로 Redis와 조회수 테이블 분리를 적용했고, 다시 테스트하면서 성능 개선뿐 아니라 데이터 정합성까지 함께 검증해야 한다는 기준을 갖게 되었습니다.

데이터베이스 마이그레이션과 Blue/Green 배포를 진행하면서는 코드만 수정하는 것이 아니라 엔티티·스키마·초기 데이터·배포 순서가 모두 연결되어 있다는 점을 배웠습니다. 작은 필드 변경도 기존 버전과의 호환성을 고려하지 않으면 배포 과정에서 문제가 될 수 있었습니다.

테스트에 대한 생각도 바뀌었습니다. 커버리지 숫자를 높이는 것보다 어떤 규칙과 실패 상황을 검증했는지가 중요했고, AI가 작성한 테스트도 목적과 assertion을 직접 확인해야 했습니다. 앞으로는 단위 테스트, 통합 테스트, 부하 테스트를 목적에 맞게 나누고, 결과를 설명할 수 있는 테스트를 만드는 것을 목표로 하고 싶습니다.
